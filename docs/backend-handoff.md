# Передача бэкендеру — актуальный сайт

Дата: 23 сентября 2026. Этот документ относится к `index.html`, `app.html`, `site.js` в **корне репозитория**. Старого `website/` больше нет. Бэкенд, БД, админка, почтовая отправка и обработчик платежей здесь не реализованы.

## Быстрый старт

1. `npm ci`, `npm run dev`. Node.js 22+. Сайт: http://localhost:4173.
2. Прочитать [OpenAPI 3.0](openapi.json). Это **целевой контракт**, уже используемый фронтендом, а не описание существующего сервера. Если сервер следует ему, менять формы и переходы не нужно.
3. Реализовать API своего стека под `/api/v1` на том же origin. Раздельный сервер подключить reverse proxy на уровне хостинга. Не открывать API через CORS без отдельного решения по сессиям и CSRF.
4. В `runtime-config.js` включить `mode: 'api'`, выключить `previewEnabled`, указать точные HTTPS origins платёжного провайдера в `paymentOrigins`.
5. `npx playwright install chromium`, `npm run check`. Браузерные API-тесты подменяют только HTTP-ответы: бизнес-бэкенда в тестах нет. До запуска продаж провести отдельный прогон **реального API и sandbox провайдера**.

`runtime-config.js` публичный: секретов в нём быть не должно. Сейчас оставлен `mode: 'offline'`, поэтому текущая публикация не отправляет данные в отсутствующий API. `previewEnabled: true` оставляет галерею для ревью; при `false` даже `?demo=1` не включает демо.

## SKU и деньги

`ceowallet-white`, `ceowallet-black`. Витринная начальная цена: 299000 копеек = 2990 RUB. Контракт API передаёт деньги **целыми копейками**, валюту `RUB`. UI переводит их в рубли при показе. В одном заказе максимум два уникальных SKU, до 10 единиц каждого. `/catalog` возвращает текущий предел и доступность каждого варианта; сервер всегда перепроверяет их.

Корзина хранится в sessionStorage под `ceo-cart-v1` в формате `[{colour:'white',quantity:1}]`. Перед запросом преобразуется в `[{variantId:'ceowallet-white',quantity:1}]`. Изменение цены не требует миграции корзины. Цена, скидка и итог **не отправляются клиентом** как доверенные значения.

NFC CARD и NEXT ITEM — тизеры. Они не имеют SKU для покупки, цены и кнопки оплаты.

## Сессия, доступ и ссылки

- `GET /session` создаёт/возвращает сессию и `{csrfToken, accessGranted, membershipAllowed}`. Cookie `ceo_session`: HttpOnly, Secure в production, подходящий SameSite. CSRF-токен сохраняется только в памяти текущей страницы. Сервер также проверяет Origin и CSRF всех POST, ограничивает частоту запросов и перебор кодов.
- Каждый POST содержит `X-CSRF-Token` и `Idempotency-Key`. JSON. Секретов/кодов в URL запросов нет.
- `POST /access/check` проверяет код и **на сервере** даёт сессии право на покупку. Ответ `{accepted:true}`. Код не сохраняется во frontend storage. Сервер определяет срок действия, резервирование и атомарное использование кода при подтверждённой оплате.
- QR-ссылка: `/app.html?screen=application#invitation=OPAQUE_TOKEN`. Фрагмент удаляется через history API сразу после чтения. `POST /membership/invitations/claim` обменивает его на право заполнить анкету в этой сессии. Это право снова проверяется сервером при POST анкеты. Необязательное поле `invitation` в анкете — реферальный код, оно **не заменяет** QR-доступ.
- Ссылка из письма на заказ: `/app.html?screen=order#order=OPAQUE_TOKEN`. `POST /orders/claim` возвращает `orderId` и даёт сессии доступ только к этому заказу. После обмена адрес содержит только `orderId`.
- Возврат с платёжного сервиса: `/app.html?screen=processing&orderId=ORDER_ID`. Получение статуса требует авторизованной cookie-сессии; при её утрате клиенту нужна ссылка из письма.
- `orderId`, `?screen=thank-you` и `?demo=1` не предоставляют права на сервере. Каждый GET заказа проверяет владельца. Все ответы персональных API: `Cache-Control: no-store`.
- Статус членства — `GET /membership/status`. Экран одобрения показывается только при `approved` от сервера.

Сервер должен сохранять CSRF-токен действующим на время сессии или поддерживать несколько открытых вкладок. Фронтенд не читает cookie, не содержит JWT и не отправляет токены на сторонние origins.

## Оформление и доставка

1. Пользователь заполняет checkout и согласия. Кнопка «Рассчитать доставку» отправляет `/checkout/quotes` с SKU/количеством, контактами, адресом и согласиями.
2. Сервер возвращает `id`, `expiresAt`, нормализованные позиции, `subtotal`, `delivery`, `total`, `currency`. Запрос **не создаёт заказ и платёж**. Quote привязан к сессии, корзине и адресным данным; сервер рассчитывает всё заново и задаёт срок действия.
3. Интерфейс показывает окончательную доставку и итог. Только отдельный клик «Подтвердить …» отправляет `POST /orders` с `quoteId`, контактами и согласиями. Любое изменение формы сбрасывает расчёт.
4. Сервер атомарно проверяет доступ, quote, остатки, сумму, адрес, согласия и создаёт заказ. Один quote должен порождать не более одного заказа, даже при разных ключах после перезагрузки. При устаревшем quote — `QUOTE_EXPIRED`, интерфейс предлагает пересчитать.
5. На экране оплаты суммы берутся из `GET /orders/{orderId}`. После нажатия кнопки `POST /orders/{orderId}/payment` возвращает платёжный URL. Карточных полей в живом режиме нет.
6. URL проверяется клиентом: HTTPS, нет login/password, origin входит в `paymentOrigins`. Сервер обязан создавать URL через выбранного провайдера и возвращать только согласованные адреса.
7. **Webhook провайдера — источник подтверждения оплаты.** Ссылка возврата не подтверждает платёж. Обновление статуса в интерфейсе делает GET заказа; автоматических повторных платежей нет.

Статусы заказа: `awaiting_payment`, `processing`, `paid`, `shipped`, `delivered`, `payment_failed`, `cancelled`. Кнопка оплаты доступна только для `awaiting_payment`/`payment_failed`. `paid`, `shipped`, `delivered` означают подтверждённую оплату. В `processing` кнопки повторной оплаты нет. Для отправленного заказа можно вернуть `tracking: {carrier, number}`; UI показывает эти данные как текст.

## Идемпотентность и ошибки

Фронтенд блокирует повторный клик на время запроса. Для повтора **того же тела в пределах страницы** сохраняет один UUID `Idempotency-Key`, включая ситуацию «сервер обработал, но ответ потерялся». Новый payload получает новый ключ. Автоматических повторов POST нет.

Сервер должен привязать ключ к сессии, операции и хешу тела; возвращать прежний результат при повторе; отказать при несовместимом теле. Срок хранения — не короче окна повторов заказа/платежа (рекомендуется минимум 24 часа). Клиентские ключи не заменяют уникальность заказа по quote и защиту от двойного списания. Повтор оплаты должен возвращать существующий активный платёж, если предыдущий ещё не завершён. Отмена fetch при уходе со страницы **не отменяет выполненную серверную операцию**.

Ошибка:

```json
{"error":{"code":"VALIDATION_ERROR","fields":{"email":"INVALID","privacy":"REQUIRED"}}}
```

`fields` опционален. Ключи — имена HTML-полей: `name`, `email`, `phone`, `city`, `address`, `comment`, `telegram`, `project`, `invitation`, `message`, `code`, `privacy`, `agreement`, `purchase-terms`. Сервер мапит вложенные поля запроса на эти имена. Сообщения для пользователя задаёт клиент; HTML, SQL и stack trace сервера не показываются.

Коды: `UNAUTHORIZED`, `FORBIDDEN`, `INVALID_CODE`, `INVALID_INVITATION`, `VALIDATION_ERROR`, `OUT_OF_STOCK`, `QUOTE_EXPIRED`, `RATE_LIMITED`, `NOT_FOUND`, `PAYMENT_UNAVAILABLE`, `SERVER_ERROR`. HTTP-статусы и схемы — в OpenAPI. Неверный успешный JSON, несовпадающие суммы, таймаут и сетевой обрыв также обрабатываются в UI.

## Заявки и хранение

Формы отправляются в `/purchase-applications`, `/contact-messages`, `/membership-applications`. Подтверждение показывается только после `{id, status:'received'}`. В sessionStorage остаётся только ID квитанции, а не текст обращения. Это локальная квитанция отправки, не авторизация и не решение команды.

Контакты, анкеты, email, код покупки, QR-токен, CSRF и карточные данные не сохраняются в localStorage/sessionStorage. При ошибке введённые поля остаются в DOM; при перезагрузке страницы исчезают. В хранилище остаются только корзина, ID заказа и квитанции. Демо-корзина отделена ключом `ceo-preview-cart-v1`; демо никогда не вызывает API.

## Что перед запуском делает бэкендер / владелец

- Реализует этот API, серверную валидацию, сессии, хранение, доставку, отправку писем, QR-приглашения и платёжный webhook; выбирает инфраструктуру и провайдера.
- Настраивает same-origin proxy и публичный runtime-config. Предпросмотр выключает при реальных продажах.
- Владелец утверждает юридические тексты, реквизиты и контакты. В `documents.js` пока есть честно обозначенные незаполненные разделы из макета — их нельзя считать готовыми документами продавца.
- Проверяет sandbox-оплату, повторные webhook, истёкший/использованный код, чужой заказ, недоступный SKU, стоимость доставки и письма на реальном сервере.

Со стороны фронтенда HTTP-точки и состояния подключены и покрыты мок-тестами. Совместимость с ещё не написанным сервером нельзя подтвердить до его реализации; при изменении контракта может понадобиться согласованная правка клиента.
