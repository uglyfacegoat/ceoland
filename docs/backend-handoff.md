# Передача бэкендеру

Фронтенд запускается без API. `website/src/integration/preview.ts` — явно демонстрационный адаптер: не делает HTTP-запросов, не отправляет контакты и не создаёт заказы. Подключить рабочий адаптер нужно через импорт в `forms.ts`. Контракты в `integration/contracts.ts` — предложение для согласования, а не описание существующего сервера.

## Каталог и корзина

| Поле                       | Значение                   |
| -------------------------- | -------------------------- |
| productId                  | `ceowallet`                |
| Белый variantId            | `ceowallet-white`          |
| Чёрный variantId           | `ceowallet-black`          |
| Цена каждого               | 299 000 копеек = 2 990 RUB |
| Технический предел корзины | 99 предметов суммарно      |

Каталог и цена находятся в `src/catalog.ts`, расчёты — в `src/cart-model.ts`. Деньги считаются в целых копейках.
В localStorage по ключу `ceomentality.cart` сохраняется `{version: 2, items: [{variantId, quantity}]}`. Старый `ceomentality.cart.v1` с количеством мигрирует в белый SKU. Повреждённая запись требует явного сброса; ошибки записи показываются пользователю. Изменение корзины в другой вкладке обновляет сумму и состав оформления, не стирая контакты.

Худи, кепка и футболка — концепты `coming-soon`. Их выбор в футере меняет только презентацию. Добавление в корзину и цена недоступны. Перед продажей нужны утверждённые SKU, характеристики и серверная доступность.

## Точки подключения

| Действие           | Метод                                | Ожидаемый ответ                               |
| ------------------ | ------------------------------------ | --------------------------------------------- |
| Проверка кода      | `checkAccess(code, signal)`          | accepted или rejected с безопасным сообщением |
| Запрос приглашения | `requestInvitation(request, signal)` | mode и идентификатор принятой заявки          |
| Оформление         | `createCheckout(request, signal)`    | URL платёжного перехода от сервера            |

Контракт оформления теперь передаёт **массив items**, а не прежние productId/quantity в корне:

```json
{
  "items": [
    { "productId": "ceowallet", "variantId": "ceowallet-white", "quantity": 1 },
    { "productId": "ceowallet", "variantId": "ceowallet-black", "quantity": 2 }
  ],
  "customer": {
    "name": "Имя покупателя",
    "email": "buyer@example.com",
    "phone": "+79991234567",
    "address": "Город, улица, дом"
  },
  "accessCode": "ПЕРСОНАЛЬНЫЙ-КОД",
  "consents": { "privacy": true, "terms": true, "purchase": true }
}
```

Цена не отправляется как доверенное значение. Сервер повторно проверяет SKU, цену, остатки, количество, доставку, код и согласия. Интерфейс показывает только стоимость товаров; итог доставки должен поступать с сервера.

## Формы

`src/form-validation.ts`: обязательность, имя, email, телефон, длина адреса и кода, согласия. Ошибки появляются после попытки отправки; затем пересчитываются при исправлении поля. Первая ошибка получает фокус, сообщения связаны через aria-describedby и aria-invalid. Формы используют novalidate — стандартных браузерных уведомлений нет.

Телефон допускает российские 10 цифр, 11 цифр с 7/8 и международный номер с `+` (8–15 цифр). Перед отправкой убираются разделители, российские варианты приводятся к +7. Это проверка формата, не существования номера; адрес email также не подтверждается на клиенте. Серверная валидация обязательна.

Контакты и код не записываются в localStorage, URL или логи. Повторная отправка блокируется на время операции; уход со страницы отменяет ожидание через AbortSignal. После проверки кода данные и корзина проверяются повторно, поскольку пользователь мог изменить их за время ожидания.

## Что подключить перед рабочим запуском

1. Реализовать адаптер с валидацией JSON-ответов, таймаутами, отменой и понятными безопасными ошибками. Не выводить сырые серверные исключения пользователю.
2. Удалить демо-код и пометки демо после подключения API. Успешную заявку показывать только после подтверждённого ответа сервера.
3. В mountCheckout обработать ответ createCheckout вместо текущего сообщения о неподключённом переходе. Проверять HTTPS и согласованный список платёжных доменов перед redirect.
4. Подключить расчёт доставки, серверную цену и остатки. Не считать принятый в браузере код авторизацией: `/access/accepted` доступен напрямую.
5. Обеспечить серверную идемпотентность оформления, атомарное использование приглашения и подтверждение оплаты по событию провайдера.
6. Согласовать сессию, CORS/CSRF, защиту от перебора кодов и частоты заявок. Предпочтителен API того же origin. Секреты не должны попадать в Vite/client env.
7. Получить документы, реквизиты, контакты и подтверждённые характеристики от заказчика.
8. Повторить сценарии с реальными ответами API и платёжного провайдера.

Домен пока не выбран. `VITE_SITE_URL` предназначен только для публичного адреса сайта; инструкция — в `seo-and-deployment.md`.
